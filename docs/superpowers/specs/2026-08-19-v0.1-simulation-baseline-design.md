# V0.1 Reusable Mobile Manipulation Simulation Baseline Design

## 1. Goal

Build a reusable ROS 2 simulation baseline for mobile-manipulation research in a known greenhouse world. V0.1 must demonstrate a complete, explainable workflow from predefined route execution to stop-and-settle gating, known target/viewpoint selection, arm planning/execution, retract, and route continuation.

The baseline is infrastructure, not a perception demo. It must keep navigation, manipulation, world semantics, mission execution, and operator interaction separated by stable interfaces so later research can replace one layer without rewriting the others.

## 2. Frozen V0.1 scope

V0.1 includes:

- a `greenhouse_v1` world definition;
- a reusable scene description containing semantic tomato targets and predefined viewpoints;
- a predefined waypoint/reference-path route format;
- a mission state machine for route execution, operation stops, settling, arm release, retract, and continuation;
- mobile-base adapters for an MK Mini profile and a second AgileX/松灵 profile;
- Nav2-facing navigation interfaces;
- MoveIt 2-facing manipulation interfaces;
- a Gazebo simulation backend;
- RViz-based operator interaction for selecting a known target/viewpoint and visualizing planned arm motion;
- trajectory/state-transition recording;
- one-command bringup as the final V0.1 integration target.

V0.1 explicitly excludes:

- tomato detection or visual localization;
- VLM/LLM planning;
- automatic grasp-point estimation;
- dynamic-obstacle reasoning;
- simultaneous whole-body base-arm control;
- real-hardware execution.

## 3. Architectural principle

The system is split into five layers:

1. **Scene layer** — owns world truth and semantic target/viewpoint definitions.
2. **Mission core** — owns task state, route progression, settling rules, and action release conditions. It contains no ROS, Gazebo, Nav2, or MoveIt dependency.
3. **Navigation adapter** — translates mission commands into Nav2 actions and reports navigation/base-motion state back to the mission core.
4. **Manipulation adapter** — translates selected target/viewpoint commands into MoveIt planning/execution requests and reports arm state back to the mission core.
5. **Simulation/UI layer** — Gazebo provides physics; RViz provides human selection and visualization.

The mission core depends only on plain data structures. Adapters depend on the core, never the reverse.

## 5. World and semantic model

The canonical world frame is `map`.

Each semantic target has:

- stable string `id`;
- class label;
- known pose in `map`;
- zero or more predefined viewpoints;
- zero or more manipulation poses.

A viewpoint and a manipulation pose are intentionally different concepts. A viewpoint defines where a camera-bearing link should be placed to observe a target; a manipulation pose defines where the manipulation TCP should be placed to operate on a target.

Initial `greenhouse_v1/scene.yaml` will contain synthetic, explicitly known targets. Later perception modules may replace the source of target poses while keeping the same semantic-target interface.

## 6. Route model

A route is an ordered sequence of waypoints. Each waypoint has:

- stable `id`;
- planar pose `(x, y, yaw)` in `map`;
- `behavior`: `pass` or `operate`;
- optional semantic target/viewpoint binding for deterministic demo missions.

The route model does not contain Nav2 implementation details. The navigation adapter owns conversion from route waypoints to Nav2 goals.

## 7. Mission state machine

V0.1 states are:

```text
IDLE
  -> NAVIGATING
  -> SETTLING        (only for an operate waypoint)
  -> ARM_READY
  -> ARM_MOVING
  -> ARM_READY        (after a non-final arm move, e.g. viewpoint move)
  -> RETRACTING
  -> NAVIGATING       (continue route)
  -> COMPLETED

Any adapter-level failure may transition to FAILED.
```

The core must reject invalid transitions instead of silently accepting them.

### 7.1 Settling gate

An operation waypoint does not release the arm immediately after a navigation-success event. The base must satisfy both:

- `abs(linear_speed) <= 0.01 m/s`;
- `abs(angular_speed) <= 0.01 rad/s`;

continuously for at least `0.5 s`.

If either threshold is exceeded before `0.5 s`, the stable-time accumulator resets.

These values are V0.1 defaults and are represented as configuration, not hard-wired policy in the state machine API.

## 8. Base profiles

V0.1 provides named profiles rather than coupling mission logic to a robot model.

### MK Mini

The simulation profile is Ackermann-oriented. Existing `agt_navigation_v2` platform geometry is provisional, so the new repository must mark unverified geometry as such and avoid presenting it as calibrated physical truth. A later CAD/measurement pass may replace visual/collision geometry without changing mission interfaces.

### AgileX / 松灵

V0.1 reserves one second base profile behind the same adapter interface. Exact product-specific geometry/controller parameters are isolated in that profile and must not leak into the mission core.

## 9. Interfaces

### Mission core input events

- `StartRoute`
- `NavigationSucceeded`
- `NavigationFailed`
- `BaseMotionSample(linear_speed, angular_speed, dt)`
- `ArmMotionStarted`
- `ArmMotionSucceeded`
- `ArmMotionFailed`
- `RetractStarted`
- `RetractSucceeded`

### Mission core outputs

- current `MissionState`;
- current waypoint index/id;
- whether navigation is requested;
- whether an arm operation is permitted;
- whether retract is requested;
- terminal result (`COMPLETED` or `FAILED`).

### Navigation adapter

Mission-side semantic API:

```text
navigate_to(waypoint)
follow_route(route)
cancel()
is_stopped()
```

The first ROS 2 adapter will map these semantics to Nav2 actions.

### Manipulation adapter

Mission-side semantic API:

```text
plan_to_named_target(target_id, pose_id)
execute_last_plan()
retract()
```

The first ROS 2 adapter will map these semantics to MoveIt 2.

## 10. Operator interaction

RViz is the V0.1 operator surface. The target interaction contract is:

1. select a semantic target;
2. select a named viewpoint/manipulation pose or use an interactive marker;
3. request plan;
4. inspect the visualization;
5. execute;
6. request retract/continue.

The operator panel is a client of the scene server and arm adapter; it is not the owner of mission state.

## 11. Recording

Each run must be representable by a run directory containing at minimum:

```text
run_<id>/
├── mission_events.csv
├── target.yaml
├── joint_trajectory.csv
└── tcp_trajectory.csv
```

The recorder should preserve timestamps and identifiers so later experiments can compare viewpoints, planners, and base-placement strategies.

## 12. Testing strategy

Testing is layered:

- **unit tests** for mission-state transitions and settling behavior without ROS;
- **schema/contract tests** for world and route definitions;
- **ROS adapter tests** for message/action translation where practical;
- **launch/integration tests** for process startup and interface availability;
- **target-machine Gazebo/Nav2/MoveIt acceptance** for the final V0.1 demo.

Production behavior is developed with RED -> GREEN -> REFACTOR cycles.

## 13. V0.1 acceptance criteria

V0.1 is complete only when all of the following are demonstrated:

1. `greenhouse_v1` launches.
2. A configured mobile manipulator spawns.
3. A predefined route is loaded and followed.
4. The robot automatically stops at an `operate` waypoint.
5. Mission state enters `SETTLING` and does not enter `ARM_READY` until the configured settling condition is satisfied.
6. A user can select a known tomato and viewpoint.
7. A MoveIt trajectory can be planned and visualized before execution.
8. The simulated arm executes and retracts.
9. Route execution can continue afterward.
10. Mission events and trajectories are exported.
11. The integrated demo is launched through one bringup entry point.

## 14. Deferred research extensions

The following are deliberately future versions, not hidden V0.1 work:

- V0.2: automatic base-placement scoring using navigation cost, IK feasibility, joint-limit margin, manipulability, and collision cost;
- V0.3: automatic viewpoint planning;
- V0.4: perception-generated semantic targets;
- V0.5: task planning/TAMP over mission actions;
- V0.6: local simultaneous base-arm whole-body motion.
